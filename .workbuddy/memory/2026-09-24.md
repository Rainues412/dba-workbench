## 第六轮：统一全部图标视觉尺寸（新增 normalize_icon.py）
- 用户反馈「各个图标大小不一致」。量化后确认：**框都是 20×20，但框内图形实际尺寸相差 1.68 倍**（MySQL 11.9px ↔ Oracle/Linux 20.0px），根因是各源图内部留白差异极大（图形占画布 33.6% ~ 95.9%）
- 归一化前实测：其他 19.6px(95.9%) / Linux 20.0px(94.6%) / PostgreSQL 19.5px(86.3%) / Oracle 20.0px(63.3%，横向文字标) / Redis 13.3px(66.7%) / SQL Server 13.0px(38.7%) / MySQL 11.9px(33.6%)
- **方案**：裁到图形包围盒 → 最长边缩放到固定 glyph → 居中贴到方形透明画布。全部统一为 256×256 画布 + 205px 图形（80%），最长边全部精确等于 **16.02px（ratio 1.00x）**
- **高分辨率归一化**（256 而非 20px）：源图 300-512px，直接压到 20px 会丢细节，视网膜屏（20px CSS 槽需 40 物理像素）会发虚；交给浏览器做最终降采样
- **Redis 是 SVG，归一化方式不同**：不重采样，只收紧 viewBox + 同比例改 stroke-width。`viewBox="0 0 24 24"` → `"2 1 20 20"`（图形 16/20 = 80%，与 PNG 一致），`stroke-width` 1.5 → 1.25 保持渲染笔画仍是 1.25px。只改 viewBox 会让所有线条变粗
- **归一化过程中踩到 4 个真实陷阱（全部已修 + 写入 skill）**：
  1. **量化桶中点当颜色** → `#dc2626`(220,38,38) 变成 (216,40,40)，肉眼正常但数千像素 off-target。修：`flat_rgb` 返回**精确**主色，量化只用于"是否单色"判定
  2. **`paste(img, pos, img)` 带 mask 混合** → 与透明黑画布做 `dst*(1-a)+src*a`，边缘 RGB 被拉向黑色。修：**不带 mask** 直接粘贴，RGB/alpha 原样拷贝，合成交给浏览器
  3. **重采样 RGBA 而非只重采样 alpha** → PIL 逐通道独立插值，LANCZOS 负瓣在高对比边缘过冲，Oracle (220,38,38)→(223,39,39)、Linux (245,158,11)→(251,162,11)。修：这类图是"单色 + alpha 蒙版"，**只缩放 alpha 通道**，RGB 保持恒定；多色图才回退完整 RGBA 重采样
  4. **LANCZOS 振铃留下轮廓外光晕** → PostgreSQL faint 从 0.29% 飙到 **7.06%，其中 3.50% 距图形 >2px**（空白画布里的孤立噪点，不是抗锯齿）。实测各滤镜：LANCZOS 远端 3.50% / BILINEAR 0% / BICUBIC 0% / BOX 0% / NEAREST 0%，但 BOX、NEAREST 会糊掉细线（SQL Server 显示尺寸下笔画仅 0.4px）。修：保留 LANCZOS + **alpha 钳制**（`clamp<=8` → faint 0.99%、远端 0.00%、peak alpha 仍 255）
- **教训：`faint%` 单看数值无法判断重采样图好坏**——正常抗锯齿和背景泄漏都落在这个区间。必须**空间区分**：从实心图形做 BFS，统计距图形 >2px 的 faint 占比；接近 0 = 健康边缘，占比大 = 振铃或背景泄漏。`verify_icon.py` 的 2% 平面阈值区分不了这两者
- **我自己引入的连带缺陷**：`regenerate_all.py` 只跑 recolor，而线上载荷已是 recolor+normalize 产物 → 把每个图标都误报 STALE（MySQL len 11656→7640），校验工具从此不可信。修：补 normalize 步骤（需 Pillow，加 `--python` 指向 venv 解释器）+ `--no-normalize` 开关；同时删掉编辑残留的重复 `os.remove(tmp)`（会 FileNotFoundError）
