### 回滚方式选择：切分支而非 reset --hard

因为改动完整保留在独立分支，用 `git checkout main` 即可回滚，**完全可逆**；
`git reset --hard` 会让后端代码不可恢复，属于不必要的破坏性操作。

执行顺序：
1. **先备份唯一数据副本** `cp server/workspace.db _rollback-backup-20260928/`，
   校验 sha256 一致（`52fa4d21...`）、SQLite 可独立打开、583 行完整
2. `git stash push -- .gitignore` 保存未提交改动（可逆，不丢弃）
3. `git checkout main` → HEAD 回到 `a75aef8`
4. 核验：工作台 sha256 与 blob 均未变、已跟踪文件干净、后端提交仍在 `feat/server-merge`

### 教训

- **"回滚"必须先侦察再动手**：跨天、且自己上轮没改文件时，"本次修改"的指代是模糊的。
  先查 git log / reflog / branch / status，确认改动范围与可逆性，再选最小破坏的方式
- **有破坏性替代方案时优先选可逆的**：改动在独立分支上 → 切分支即可，不要用 reset --hard
- **回滚前先备份 git 未跟踪的唯一副本**：`workspace.db` 不在任何提交里，checkout 虽不删它，
  但后续任何清理动作都可能误删
- **git 回滚 ≠ 线上回滚**：资料库发布态是独立的一份产物，本地分支切换对它毫无影响
- **查线上产物要用接口返回的 path**，不要沿用上轮记住的文件名，否则会把 NoSuchKey
  错误页误读成"线上被破坏"
